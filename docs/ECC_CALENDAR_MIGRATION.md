# ECC Calendar：从网页迁移到微信小程序

## 当前版本的边界

网页端负责验证活动日历、筛选、活动详情和报名入口。当前活动为体验数据，暂不保存报名者个人信息，也不创建真实支付订单。

## 已经为迁移保留的结构

- `shared/calendar.ts`：平台无关的活动类型和活动数据模型。
- `/api/calendar/events`：活动列表的 HTTP 接口雏形。
- `/calendar`：网页端日历界面。
- `/calendar/[slug]`：网页端活动详情界面。

网页界面不是未来小程序的数据源。网站和小程序应共同调用后端 API，因此迁移时只需要重新实现微信小程序的 WXML、WXSS 和交互层。

## 正式后端的数据实体

1. `Organizer`：主办方。第一阶段只有北雍，仍保留该实体以支持未来多主办方。
2. `Event`：活动内容、分类、线上/线下、时间、地点、封面、报名规则。
3. `TicketType`：免费票、付费票、邀请票、价格、库存与销售时间。
4. `User`：微信 OpenID/UnionID、昵称以及经用户授权提交的联系信息。
5. `Booking`：用户与活动的预约关系。
6. `Order`：支付金额、微信支付单号和订单状态。
7. `Refund`：退款金额、原因与微信退款状态。

建议订单状态：

`pending_payment → paid → confirmed → cancelled → refunding → refunded`

## 微信小程序迁移顺序

1. 将静态活动数据迁入腾讯云 CloudBase 数据库。
2. 把当前 HTTP 接口替换为 CloudBase 云函数或腾讯云 API。
3. 网页端继续调用同一组 API。
4. 使用微信小程序原生组件实现月历、活动列表和活动详情。
5. 接入微信登录，以 OpenID 建立用户身份。
6. 接入微信支付：后端创建订单，前端调用 `wx.requestPayment`，以后端支付通知确认成功。
7. 加入名额锁定、超时释放、退款、通知和签到能力。

## 不应与平台绑定的字段

活动分类固定为：长风沙龙、长风论坛、北雍课程、其他活动。

举办方式单独记录为：线上、线下。

不要把活动分类和举办方式合并，也不要把微信支付状态直接写入活动表。
